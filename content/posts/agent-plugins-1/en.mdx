Coding-agent features grew quickly in 2026, and their formats fragmented with them: one product has skills, another has commands, and external tools arrive through MCP. Once capabilities need to move between teams and clients, packaging becomes the next problem.

Skills, commands, hooks, and MCP servers can require different directories and configuration in each tool. Agent Plugins 1.0 aims to bundle them into an installable unit.

A skill tells an agent how to perform a task. An MCP server provides external tools it can call. A plugin is the outer package that installs those capabilities and their configuration together.

Several companies participated in the standard, with the goal of making one plugin usable by different agent clients. Products can retain specialized features, so agents do not become identical, but teams repeat less work organizing the same skill and MCP configuration.

Matt Pocock's personal skills from February show the earlier stage of the problem. Six months later, the ecosystem was discussing not only how to write a skill, but how to install, share, and manage it.

## Separating Skill, MCP, and Plugin

- A Skill is an instruction manual for the steps an agent should follow.

- An MCP server supplies tools such as querying a database, reading a design, or controlling deployment.

- A Plugin is the installation and distribution unit that can carry both plus configuration.

The layering is familiar to frontend developers: component documentation, the API it calls, and the package published to npm are different things. Agent vendors initially defined the outer packaging independently and are now trying to align it.

Cross-tool does not mean perfectly identical behavior. A plugin may include client-specific features, and companies still need to limit what an MCP server can access. The standard addresses installation and discovery, not a promise that every client behaves exactly the same.

This is more noteworthy to me than one more AI feature. Once plugins can be shared and centrally managed, a coding agent begins to resemble a maintainable development environment instead of a box of prompts assembled separately by each engineer.

Installability also brings traditional package-management questions back: who publishes it, whether updates arrive automatically, what hooks execute, and which data an MCP server can read. I would not let a newly discovered plugin touch production. Reading the manifest, pinning a version, and testing without sensitive credentials remain effective habits in the agent era.

An internal plugin has a direct benefit. Bundling issue triage, project verification commands, and company documentation gives a new teammate more than a prompt; it gives them a repeatable, reviewable path through the work. If the standard matures, I hope this governability matters more than simply adding more Install buttons.
